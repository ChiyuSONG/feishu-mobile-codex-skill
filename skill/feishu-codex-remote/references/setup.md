# Setup And Repair

## One-Prompt Setup

1. Resolve the current working directory and show its folder name as the proposed project name. Inspect the exact source task configuration using the provisioning contract in SKILL.md. Explain its effective permission before changing the machine: Full Access allows reading, writing and running tools across the machine while task scope remains the registered project. State the larger blast radius and the conversational alternatives `project-only-auto` and `auto-review`. Preserve inherited permission unless the user changes it; missing source settings require confirmation.
2. Run `python scripts/bootstrap.py check`. Support Windows and macOS; stop with a clear prerequisite if the platform or Python is unsupported.
3. Run `python scripts/bootstrap.py install` to create the isolated runtime and install pinned dependencies.
4. Open the Feishu Open Platform in the user's signed-in browser. Prefer computer-use for navigation and let the user scan the QR code or complete CAPTCHA. Before CUA clicks any create-app control, read the visible account/tenant selector and determine whether the current identity is personal or team/company/enterprise. Default to and recommend a personal account for first-time setup. Treat an unknown or ambiguous account type as non-personal: pause, explain that a team app may be visible to the organization and require administrator approval, and ask the user to switch to a personal account. Continue in a team account only when the user's stated goal explicitly targets a group under that tenant and the user confirms that specific tenant after accepting those implications. Silence and a broad request to automate setup are not consent. Record the verified account type and any team-tenant opt-in in the setup summary.
5. After the account-type gate passes, and before creating any app, produce a sanitized inventory from known user-level gateway/publisher registries, Listener configurations, protected credential metadata, and the approved tenant's self-built apps. Verify tenant, ownership, bot and long-connection capability, document delivery, required scopes, credential availability, and Listener topology. Reuse a verified compatible app and extend only the required capabilities. Create a new minimum app only after recording why every candidate is unsafe or insufficient, or after the user explicitly requests isolation. Do not migrate working legacy apps as a side effect. Enable `im.message.receive_v1` and grant only the operations used by the gateway: receive group messages, send/reply messages, read group history for reconciliation, get and upload message image/file resources (`im:resource` or the current equivalent), manage reactions, create/read the private group, import/manage private documents, and create/update Docx blocks plus upload Docx images/files (`docx:document` and `drive:drive`). Treat this as an installation preflight gate: while the user is already completing login and consent, ask them—or their tenant administrator when required and explicitly approved—to approve every missing operation, especially native image/file upload. Saving permissions, event subscriptions, or long-connection settings in the console is not proof that they are active: complete any required app-version creation, release, enablement, or approved review, then verify the effective version can receive a real user message and read history. A bot that can only send messages has not passed setup. Do not continue to project binding, welcome, or the success report while any required permission or activation step is missing. Explicit image artifacts must be sent as native Feishu image replies and may also be embedded in a private document. Native media insertion must be read back and verified; if an existing app lacks Docx permission, preserve document delivery and expose the artifact as a private downloadable file rather than silently omitting it.
6. Add the localhost OAuth redirect URI `http://127.0.0.1:17321/callback`. Never request a public callback or public endpoint.
7. Store the App Secret without echo using `python scripts/feishu_publish.py configure --app-id <id>`. On macOS this uses Keychain; on Windows it uses DPAPI. Then run `python scripts/feishu_publish.py auth`; the browser authorization is the preferred QR/login moment for private-document delivery.
8. Register the exact working directory with `remote_gateway.py init-project --language <zh-CN|en>` and the source-task profile arguments documented in SKILL.md. Omitted permission inherits the confirmed source setting, not an automatic elevation. Infer the system-message language from the user's setup request, defaulting to Chinese when ambiguous. Default the Feishu group display name to `Codex · <folder-name>` and explain that it may be renamed. Create the private group or bind the explicitly selected existing group by stable `chat_id`. Before binding an existing multi-member work group, explain that member messages delivered to the bot may invoke local Codex, verify the intended member scope, and agree on the local permission profile; team-tenant consent alone is not consent for unrestricted member access.
9. Install the demand-start launcher with `python scripts/listener_control.py`. Do not add boot or logon triggers. On macOS, verify the generated LaunchAgent contains the absolute Codex executable discovered during preflight as `CODEX_CLI_PATH`; `launchd` does not inherit the interactive shell environment. Start it once through non-destructive `launchctl kickstart` semantics, verify a repeated SessionStart does not kill or restart an already-running Listener, confirm it can read the current user's Keychain credential without reporting it missing or inaccessible, and keep setup incomplete if any check fails.
10. Install the user-level Codex SessionStart Hook with `python scripts/install_startup_hook.py install`. Preserve existing hooks. Ask the user to review and trust the exact `Starting Feishu Remote Listener` command when Codex prompts; never bypass trust.
    This step changes Listener startup only. Inventory existing project Automations before and after installation and verify their cadence, status, prompts, usage-report behavior, reminders, and domain-specific work are byte-for-byte unchanged.
11. Start the Listener, run an end-to-end message/reply test, and send one explicit in-project image through the persisted thread. Confirm it appears as a native Feishu image message; a local file, private-document fallback, or synthetic mock is not sufficient. Temporarily interrupt and restore the long connection, confirm reconnect causes an immediate history reconciliation, then simulate one missed event and confirm the next hourly inspection retrieves it for an opted-in project. Empty reconciliation must not start Codex. If Feishu still returns `99991672` or another permission error, return to the permission preflight, request the missing scope, and repeat the real test. Keep setup incomplete until the user confirms the image is visible. Only then send the Feishu welcome message and install the active hourly Automation. Its sync command must include `--inspection-report`: the report follows the project's persisted mode described in [Automatic Inspection](../SKILL.md#automatic-inspection). Verify the first registered project gets the full report and additional new projects get only status from their first inspection, including while idle, without querying usage. While a task is `processing`, verify the first line reports elapsed time plus the latest safe user-visible Codex update and the inspection still returns immediately; when the default report is disabled, verify a progress-only message is sent while active and no progress-only message is sent while idle.
12. Report the selected inspection mode (full or status-only), Codex permission mode and its downgrade command or conversational instruction, granted Feishu permissions, credential backend, runtime directory, launcher, SessionStart Hook and trust state, Automation cadence and Codex-usage effect, document privacy setting, language, and anything that still needs manual work.

## Required User Actions

Ask only when the action is actually reached:

- scan/login to Feishu;
- switch to a personal account when the current account is a team/company identity, or explicitly opt in to that specific team tenant after the administrator-approval and organizational implications are explained;
- approve the requested Feishu app permissions and OAuth consent, including native image/file delivery (`im:resource` or the current equivalent);
- review and trust the exact Codex SessionStart Hook;
- securely paste the App Secret if browser automation cannot transfer it without exposing it;
- obtain tenant-admin approval during this initial authorization phase only after the user has explicitly opted in to using that team tenant.

Never ask the user to invent project keys, chat IDs, thread IDs, state paths, listener commands, or routing variables.

## Welcome Surfaces

The Skill itself cannot assume an unsolicited post-install chat message. Provide the starting sentence in `agents/openai.yaml` and the GitHub README. After the first invocation, give a short Codex-side setup summary. After binding, send the Feishu welcome message. Welcome and scheduled inspection content must reflect the project's report mode; see [Automatic Inspection](../SKILL.md#automatic-inspection). Do not duplicate shared usage, tips, reminders, or DIY behavior in additional new projects.

## Uninstall

Map `断开当前项目` to project scope and `卸载飞书远程 Codex` to all-project scope. Run `python scripts/uninstall.py --scope project --project-key <key>` or `python scripts/uninstall.py --scope all` first without `--apply`; show its JSON preview in plain language and verify that the resolved targets belong to this Skill.

If no target message is pending or processing, run the same command with `--apply --confirm`. Project scope removes only that binding and its scheduled inspection, then restarts the shared Listener when other bindings remain. All-project scope removes every owned scheduled inspection, the owned SessionStart Hook, and the owned Listener launcher. Both preserve local recovery state by default. Remove the installed `feishu-codex-remote` Skill directory only when the preview identifies it and no project bindings remain; never remove the source repository or another Skill with the same name.

Use `--purge-local-data` only after the user explicitly asks to delete credentials, queue history, logs, and recovery state. Treat that option as irreversible. Never delete Feishu conversations, groups, or generated documents. If active work exists, stop and list the affected message IDs; use `--abandon-active` only after the user explicitly chooses to abandon them.

## Repair

Preserve messages and state. Diagnose config, OS credential backend, Listener launcher, events, durable queue, thread state, Feishu history, and document OAuth before changing anything. Reconcile the exact project after a repair. Apply a graceful cross-platform reload with `python scripts/reload_gateway.py`; use `--request-only` when the current Feishu turn is itself running inside the Listener. Never reset a cursor or delete pending/processing/failed messages to make status look healthy.
